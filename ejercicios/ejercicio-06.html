Ejercicio: Aplicación del ASVS de OWASP a una aplicación web sencilla

Parte 1: Entendiendo el ASVS (Teoría)

Tarea: Antes de usarlo, necesitas saber qué es. Responde brevemente a estas preguntas:

1. ¿Cuál es el objetivo principal del ASVS de OWASP?

El objetivo principal de ASVS (Application, Security, Verification, y Standard) es definir requisitos o estándares de seguridad para aplicaciones y servicios web.

2. El ASVS se divide en tres niveles. En tus propias palabras, ¿cuál es la diferencia clave entre los niveles 1, 2 y 3?

La razón por la que ASVS divide por niveles en base a el nivel de importancia empezando por bases que cubren vulnerabilidades críticas (nivel 1), hasta metodologías de defensa para un alto nivel de seguridad (nivel 3)

3. Explora el ASVS más reciente en el sitio web oficial. Encuentra el Capítulo 1 (Codificación y Saneamiento) y el Capítulo 6 (Autenticación). Revisa algunos requisitos. ¿Qué observas sobre su redacción?

Se puede observar que los requisitos del ASVS se redactan como afirmaciones verificables y breves: empiezan por "Verify that", cubren un solo control, indican el nivel y se centran en el resultado y no en la herramienta. Esa es la base de por qué sirven tanto para auditar como para convertirse en tests. Es decir, todos los capitulos estan escritos de manera como si fuera un checklist, para que los desarrolladores puedan consultarlo conforme

Parte 2: Análisis de un escenario (Práctica)

Imagine una sencilla aplicación web de “Notas” con las siguientes características:

• Los usuarios pueden registrarse e iniciar sesión (register y login).

• Los usuarios que hayan iniciado sesión pueden crear, ver, editar y eliminar sus propias notas ( create, view, edit, and delete).

• Hay un "Panel de administración" en /admin que muestra todos los usuarios y todas las notas de todos los usuarios. Solo los usuarios con el indicador is_admin activado en la base de datos pueden acceder a él.

• La aplicación utiliza una base de datos SQL.

Fragmento de código vulnerable (pseudocódigo):

# View a specific note

@app.route('/note/<note_id>')

def view_note(note_id):

user = session.get('current_user')

# VULN: SQL Injection possible and no access control check! query = "SELECT * FROM notes WHERE id = " + note_id

return render_template('note.html', note=note)

# Admin Panel

@app.route('/admin')

def admin_panel():

# VULN: Only checks if user is logged in, not if they are an admin! if session.get('current_user'):

users = database.get_all_users()

notes = database.get_all_notes()

return render_template('admin.html', users=users, notes=notes) else:

return redirect('/login')

Parte 4: Desafío adicional: Cómo escribir una función segura

Tarea: El gerente de producto desea una nueva función: los usuarios ahora pueden compartir una nota con otros usuarios generando un enlace para compartir.

Utilizando el ASVS como guía, escribe una lista de consideraciones y requisitos de seguridad que se deberían implementar para que esta función sea segura. Consulta capítulos o requisitos específicos del ASVS.

Piensa en:

• ¿Cómo se genera el token (abc123-def456)? (V11: Criptografía)

Deberia de cumplir el punto 11.5.1, donde se remarca que el generador de numeros aleatorios CSPRNG, debe ser de 128 bits de entropía

• ¿Se puede adivinar el enlace? (V6: Autenticación)

Según el punto 6.3.1, el enlace debería ser capaz de soportar ataques de fuerza bruta, para que no sea adivinable.

• ¿Se puede revocar el enlace? (V8: Autorización)

Solo el propietario de la nota debería poder crear o quitar enlaces siguiendo el punto 8.2.2, sin que se genere IDOR y BOLA (Insecure Direct Object Reference y Broken Object Level Authorization) .

• ¿Se crean datos de sesión al ver el enlace compartido? (V7: Gestión de sesiones) 2

Siguiendo el punto 7.2.5, no se debe crear una sesión para ver el enlace. Si hay login, emitir un token nuevo e invalidar el anterior.
